## 1. 처음 한 번 할 일

1. **가입 막기** — Authentication → Providers → Email → *Enable signup* 끄기 (초대제).
2. **테스트 계정 정리** — Authentication → Users 에서 `ddd` · `123` · `test@test.com` 삭제 (임시 서비스 잔재).
3. **API 노출 스키마 확인** — Settings → API → *Exposed schemas* 에 `public` 만 (기본값). `core` `crm` `raw` 가 들어가 있으면 제거.
4. **담당자 코드 확인** — admin.html → 설정 · 담당자. 초기값은 이름순 1001~. 실제 쓸 번호로 바꾸세요.
5. GitHub Pages 배포 후 매장 기기 홈 화면에 `store.html` 추가.

### 사내 도메인으로 열기 — `db.samsungat.co.kr`

1. 가비아 DNS 관리 → 레코드 추가: **타입 `CNAME` · 호스트 `db` · 값 `yonghyeonjee.github.io.` · TTL 600** — 2026-09-04 등록 완료
2. GitHub 저장소 → Settings → Pages → *Custom domain* 에 `db.samsungat.co.kr` 입력 → Save → 몇 분 뒤 *Enforce HTTPS* 체크
3. 저장소 루트에 `CNAME` 파일(내용: `db.samsungat.co.kr` 한 줄)을 추가. Pages 가 이 파일을 보고 커스텀 도메인을 켭니다 — 도메인을 안 쓸 때는 이 파일이 있으면 안 됩니다

그 뒤 주소는 `https://db.samsungat.co.kr/` (고객센터) · `/admin.html` · `/store.html` 입니다.
관리자·매장 주소는 어디에도 링크하지 않습니다. 내부 코드명은 **Datacenter**, 대외 표기는 **삼성스토어 시흥**.
기존 A 레코드(`@`, `www`)는 건드리지 않습니다 — 홈페이지(`@`·`www` → 211.233.50.235)는 그대로 있고 `db.` 만 GitHub 로 갑니다.
DNS 전파는 보통 10분~1시간, 인증서 발급은 GitHub 가 자동으로 합니다.

### 1-b. 외부 공유 대시보드 붙이기 (`dash/`)

1. GAS `매출 대시보드 v4` 프로젝트에서 `tools/gas/share_patch.gs` 내용을 Code.gs 에 붙여 넣고(기존 `doGet` 은 교체), 저장
2. [배포] → [새 배포] → 유형 웹 앱 · 실행 **나** · 액세스 **모든 사용자(Anyone)** → 배포. **기존 배포는 그대로 둔다**(사내용, 구글 계정 검사)
3. 새 배포의 `/exec` 주소를 `dash/index.html` 맨 아래 `SHARE_URL` 에 넣고 저장소에 올린다
4. `https://db.samsungat.co.kr/dash/` 를 열어 3166 으로 확인

비밀번호는 정적 페이지에 없고 GAS 가 검사한다. 바꾸려면 GAS 프로젝트 설정 → 스크립트 속성 `sharePassword`. 한 번 맞으면 그 브라우저 탭에서는 다시 묻지 않는다(탭 닫으면 초기화).
데이터는 GAS 캐시(6시간·06시 갱신)를 그대로 받으므로 사내 대시보드와 숫자가 항상 같다. '데이터 갱신' 버튼만 숨겨져 있다.

**출처 토글 (현행 시스템 ↔ 대시보드 v4)** — 대시보드 상단 세그먼트. 기본은 **현행 시스템**(Datacenter `fn_dash_payload_pub`, 최근 12개월, 비밀번호 3166 서버 검사). **대시보드 v4 (기존 app)** 는 위 GAS 공유 주소. 양쪽 숫자가 맞는지 비교하는 용도이며, GAS 를 끄는 날 SHARE_URL 만 비우면 된다.

**집계 기준 토글 (수기입력 ↔ 원장)** — 현행 시스템에서만 동작. `수기입력` 은 담당자가 채널별로 적어 넣은 일매출(`core.channel_daily`), `원장` 은 주문 원천(샵링커 등 `core.orders`)에서 집계한 값. 주문수·상품·렌탈·VMS·매장은 두 기준 모두 원장 기준으로 같다. RPC 는 `fn_dash_payload(p_from,p_to,p_mode)` / `fn_dash_payload_pub(p_pw,p_from,p_to,p_mode)`.
자체 모드 원천: 온라인 채널 = `core.channel_daily`(담당자 수기 = GAS `_raw`와 동일) · 매장/구독/직판 = `core.store_daily` · VMS/렌탈 = `core.orders` · 상품/주문수 = `core.orders`.
콘솔 [매출 대시보드]는 같은 화면을 `dash/index.html?embed=1` 로 품고(로그인 세션의 `fn_dash_payload` 로 데이터 전달, 비밀번호 없음), "요약(기존)"으로 이전 구성도 볼 수 있다.

### 1-c. 홈페이지 구독문의 · 견적서 → Datacenter (`tools/gas/inquiry_forward.gs`, `quote_forward.gs`)

## 2. 기존 데이터 적재 (STEP A)

admin.html → **원본 파일 업로드**. 화면 오른쪽 위 **[양식 엑셀 받기]** 를 누르면 6개 형식의 예시 시트가 든 xlsx 를 내려받을 수 있습니다.

- **시트 이름·순서는 상관없습니다.** 파일 안 모든 시트를 훑어 헤더(열 이름 행)로 형식을 인식합니다.
- 한 파일에서 여러 형식이 인식되면 버튼이 뜨고, 골라서 하나씩 적재합니다.
  현행 `삼성앤텍 대시보드_월별 주문서` 파일 하나에서 shoplinker · vms · 렌탈 · Manual 4개가 자동으로 잡힙니다.
- 열 순서는 달라도 되고, 없는 열은 비워도 됩니다. 같은 파일을 다시 올려도 중복되지 않습니다(UPSERT).

| 순서 | 파일 | 인식 키 | 비고 |
|---|---|---|---|
| ① | 고도몰 회원 4개 (p몰·s몰·at몰·sh몰.xlsx) | 회원번호·휴대폰번호·이름 | 몰 이름을 파일명에서 자동 선택. 휴대폰 없는 회원은 건너뜀 |
| ② | 샵링커 주문 (.xls 원본 또는 대시보드 xlsx의 shoplinker 시트) | 쇼핑몰아이디·주문번호·자사주문번호 | 22,595행 ≈ 500행씩 46회 호출, 1~2분 |
| ③ | 이카운트 판매현황 (월별) | 일자-No.·품목명(규격)·공급가액 | 라인 단위. 채널 VMS |
| ④ | 렌탈 (대시보드 xlsx의 렌탈 시트) | 계약번호·청구시작일·거래처 | |
| ⑤ | 이카운트 가망고객 | 일자-No.·관심 품목명·유입경로명 | |
| ⑥ | 매장 일별 (대시보드 xlsx의 Manual 시트) | 날짜·매장-일시불 | 8/18 이전 누적분은 8/18 하루로 들어감 — 원본 그대로 |

회원을 먼저 올리는 이유: 주문의 이름+번호가 회원 마스터와 같은 키로 묶여야 "한 고객의 자사몰·매장·VMS 이력"이 한 줄이 됨.

## 2-b. 온라인 채널 (담당자 시트 대체)

`삼성앤텍_상품_주문관리 파일` 의 역할을 콘솔 [온라인 채널]이 이어받는다.

| 시트 | 어디로 | 비고 |
|---|---|---|
| 온라인 매출_YYYY년 · `_raw` | `core.channel_daily` (채널×날짜 매출/환불) | 화면에서 직접 입력 + 일괄 저장, 같은 날 원장(샵링커) 합계와 대사. 파일을 [데이터 가져오기]에 올려도 자동 인식 |
| SSG·쿠팡·롯데온 정산내역, 자사몰 미정산내역 | `core.settlement` | 지급여부·지급일·비고 인라인 수정, 직접 추가 |
| 시흥·가전시장·B2B (등록요청) | `core.listing_request` | 상태·가격 인라인 수정 |
| 쿠팡등록파일·SK스토어·토스쇼핑·수수료·재고·판매담당자N월 | (미적재) | 다음 단계: `core.listing`(채널별 판매가·공급가·수수료·마진), 재고 |

채널 표준명은 `core.f_channel_norm` (프라자몰→P몰, 에스몰→S몰, 스마트스토어→E스토어, B2B스토어→B2B, 시흥스토어→시흥 …).

### 업로드 되돌리기

[데이터 가져오기] 업로드 이력의 **되돌리기**: 고도몰 회원은 그 업로드가 붙인 몰 회원번호를 떼고 그 업로드로만 생긴 고객(거래·상담·견적 없음)을 삭제, 원장은 그 업로드가 새로 만든 행을 삭제(기존 행을 갱신한 부분은 복구 불가·건수만 표시). 고도몰 회원 적재는 몰 이름을 직접 타이핑해야 실행된다.

## 3. 매출 대시보드 보는 법

상단 남색 띠에서 세 가지를 고릅니다.

| 컨트롤 | 값 | 무엇이 바뀌나 |
|---|---|---|
| **지표** | 순매출 · 총매출 · 환불 | 상단 숫자, 기간 추이, 채널 순위·상세, 도넛 |
| **범위** | 전체 · 온라인 · 오프라인 | 서버에서 걸러서 다시 계산 (온라인 = 자사몰·오픈마켓) |
| **화면** | 개요 · 채널 · 상품·시간 | 아래 카드 묶음 |

**비교 기간은 고르는 게 아니라 자동으로 따라옵니다.** 어제→전주 같은 요일, 이번 주→전주 동기간,
지난 주→전전주, 이번 달→전월 같은 일수, 지난 달→전월 전체, 올해→전년 동기간, 직접 입력→직전 같은 일수.
KPI 카드의 ▲▼ 와 채널 순위의 회색 눈금(│)이 모두 이 기간을 가리킵니다.

- **증감 원인(워터폴)** — 전기에서 당기까지 무엇이 매출을 올리고 내렸는지. 변동 폭 상위 10개 + 기타.
  "지난달보다 왜 줄었지"에 한 화면으로 답합니다. 채널/상품 두 가지로 볼 수 있습니다.
- **대물 · 소모품 / 카테고리** — 상품명과 모델코드에서 자동 분류합니다(냉장고·김치냉장고 / 세탁·건조 / 필터·소모품 / 토너·잉크 / TV·영상·음향 …).
  건수는 소모품이, 금액은 대물이 이깁니다. 재고·프로모션 판단은 대물, 재구매 CRM 대상은 소모품 쪽에서 나옵니다.
  분류 규칙은 DB 함수 `core.f_category` 한 곳에 있습니다. '기타'가 늘면 그 함수에 키워드를 더하면 됩니다.
- **상품 파레토** — 상위 몇 종이 매출 80%를 만드는지. 재고·프로모션 우선순위의 근거.
- **요일 × 시간대** — 주문 시각 기준. 광고 집행 시간대와 매장 인력 배치에 씁니다.
  매장·VMS 처럼 시각 없이 들어온 건은 00시에 몰리므로 온라인 범위로 좁혀서 보세요.
- **데이터 점검** — 환불이 한 건도 없는 채널(= 취소·반품이 원장에 안 들어온 채널), 미마감 일수, 미처리 접수.

숫자는 모두 **서버에서 집계해서 내려옵니다.** 한 번 열 때 1~27KB. 원본 행을 브라우저로 가져오지 않습니다.

| 항목 | 정책 | 근거 |
|---|---|---|
| **로그인** | 담당자 본인의 4자리 코드. 코드를 넣으면 판매·상담의 담당자가 자동으로 본인이 됨 | 담당자 선택 누락·오입력이 사라짐. 다른 프로 대신 입력할 때만 드롭다운에서 변경 |
| **판매 건별 입력** | DPS 입력 직후, 같은 자리에서 30초 안에. 고객명·번호는 **동의받은 경우만** | 필수 항목 4개(상품명·판매가·구분·판매일)로 최소화. 상품명은 DPS 화면 그대로 옮겨 적기 |
| **일 마감** | 매일 영업 종료 시 DPS 일 합계(일시불·구독·프로별 직판)를 전기. 늦어도 **익일 오전 10시** | 대시보드 매장 매출의 1차 출처. 미마감은 매장 화면과 대시보드에 노란 배지로 표시 |
| **상담 기록** | 견적·상담 후 구매로 안 이어진 건은 당일 기록. 관심품목·유입경로·예상금액 3개는 꼭. "내일 2시" 같은 약속은 **콜백 예정**으로 | 매장 CRM ①안(미완료 상담 재연락)의 대상 목록이 여기서 나옴. 콜백은 담당자 '내 고객' 탭 맨 위에 시간순으로 뜨고, 관리자 상담 목록에 지남/예정/완료로 표시 |
| **판매 단계** | 입력 시 **매출**(DPS 매출만 잡힘, 미확정) 또는 **판매완료**(배송·설치 완료). 확정되면 '확정 대기' 목록에서 판매완료로 | 두 단계 모두 대시보드 매출에 포함. 취소·환불은 관리자 원장에서 |
| **기존 고객** | 이름 또는 번호 뒷자리로 찾아 고르면 번호를 다시 안 적어도 같은 사람으로 이어짐. 이전 구매·상담 이력이 함께 뜸 | 최근 기록의 담당 프로가 그 고객의 담당. '내 고객' 탭에 모임 |
| **방문 접수** | 매장 입구 태블릿에 `visit/` 를 띄워 둠. 연락처는 선택. 연락처 남긴 건은 접수함에서 '상담으로' 전환 가능 | 방문 목적·경로·관심 가전 통계가 접수함 상단에 집계 |
| **상담 → 구매 연결** | 판매 입력 시 "상담번호"에 SC번호 적으면 자동으로 구매완료 처리 | 유입경로별 실매출 계산의 키 |
| **수신동의** | 토글은 고객이 구두·서면으로 동의한 경우에만 ON. 기본값은 판매 ON / 상담 OFF | 광고성 발송 가능 인원(현 20%)을 매장에서 늘리는 유일한 경로 |
| **정합성 점검** | 주 1회 admin → 매장 일마감에서 (일마감 합계) vs (건별 원장 합계) 비교. 차이 10% 이상이면 미입력 확인 | 건별 입력이 정착되면 일마감을 줄여갈 수 있음 |
| **책임** | 프로별 본인 판매 건 입력. 일 마감은 당일 마감 담당(점장 또는 지정자) 1명 | 코드로 입력자가 자동 기록됨 |

일 마감이 왜 별도인가: 건별 입력은 빠지기 쉽고, DPS 합계는 정확하다. 둘을 분리해 두면 매출 대시보드는 항상 맞고, 건별 원장은 고객·상품 분석에만 쓰면서 점차 정확도를 올릴 수 있다.

## 5. 고객 식별 키 (buyer_key)

한 사람의 자사몰·매장·VMS 이력을 하나로 묶는 키. 실번호를 노출하지 않기 위해 해시로 만듭니다.

| 순위 | 조건 | 키 |
|---|---|---|
| ① | 휴대폰이 있으면 | `이름 + 숫자만 남긴 번호의 뒤 8자리` 해시 |
| ② | 번호가 없고 사업자번호·이메일이 있으면 (렌탈·VMS 거래처) | 그 값의 해시 |
| ③ | 둘 다 없으면 | 키 없음 → 고객 마스터에 안 들어가고, 원장의 `buyer_name_raw` 에 이름만 남음 |

뒤 8자리를 쓰는 이유: 뒤 4자리만 쓰면 `010-1111-9281` 과 `010-3841-9281` 이 같은 사람으로 묶입니다.
공백·하이픈은 무시하고, 마스킹된 값(`*윤*`, `010-****-9955`)은 키를 만들지 않습니다.

## 6. 보안 구조 (바꾸지 말 것)

- 브라우저는 `public` 스키마의 **함수(RPC)** 만 호출. 테이블(`core` `crm` `raw`)은 노출되지 않으며 RLS 로 전면 차단.
- 실명·실번호는 `crm.customer` 에만. 원장에는 해시 키(`buyer_key`)만.
- 실번호 표시 토글을 켜거나 발송 대상을 추출하면 `crm.access_log` 에 누가·언제·왜 기록됨.
- 매장 화면은 담당자 코드로 열리므로 **매장 기기에서만** 사용. 코드 유출 시 설정에서 즉시 변경(또는 비활성).
- `admin` 만 삭제·일괄 적재·설정 변경 가능.

## 7. 무료 플랜 운영 규칙

- 대시보드·목록은 서버 집계와 50행 페이지네이션이라 egress 를 거의 쓰지 않음. **전건 조회 코드를 추가하지 말 것.**
- 엑셀 내보내기는 기간 필수(최대 1년). 습관적으로 전체 기간을 받지 않기.
- 백업: 무료 플랜은 자동 백업 없음 → 주 1회 Supabase Dashboard → Database → Backups 또는 `pg_dump` 로 NAS 저장.
- 1주일 무활동이면 프로젝트 일시정지 → 대시보드에서 *Restore* 한 번.
