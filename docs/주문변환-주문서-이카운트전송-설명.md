# 주문 변환 · 주문서 · 이카운트 전송 — 누구나 읽는 설명

> 2026-09-06 · Datacenter(db.samsungat.co.kr) 기준. 담당자·운영자·개발자 순서로 읽으면 됩니다.

---

## 한 문장으로

**쇼핑몰에서 팔린 것을 이카운트에 전표로 올리는 일**입니다. 예전엔 코드아이에 파일을 넣고 사람이 코드를 맞춰 넣었고, 지금은 시스템이 대부분 알아서 하고 **애매한 것만 사람이 봅니다.**

```
쇼핑몰 주문 ──▶ 샵링커 ──▶ ① 자동 수집 ──▶ ② 주문서 만들기 ──▶ ③ 이카운트 전송
                          (하루 5번)      (재고 차감)         (실제 전표)
                                          ▲ 자동 68% / 사람 32%   ▲ 사람이 누름
```

---

## 담당자용 — 내가 할 일은 무엇인가

**평소엔 두 가지만 봅니다.**

1. **[주문 변환]에 남아 있는 것** — 시스템이 혼자 못 정한 주문입니다. 이유는 딱 두 가지:
   - *확인 필요* — 같은 모델에 품목이 여러 개 (예: `MLT-D111S`가 `/TND`·`1+1`·`(재생)` 셋). 어느 걸 팔았는지 데이터만으로 모릅니다.
   - *코드 없음* — 처음 보는 상품. 한 번 연결해 주면 다음부터 자동입니다.

   고르고 나서 **기억**을 켜 두면 그 상품은 다시 안 물어봅니다. 그래서 이 일은 **갈수록 줄어듭니다.**

2. **[전송]** — "전송 대기"에 쌓인 주문서를 이카운트로 올리는 버튼. 하루 한 번 눌러도 되고, 만들자마자 눌러도 됩니다. 확인창이 세 줄로 말해 줍니다: 실제 전표가 생긴다 / 여기서 되돌릴 수 없다 / 실패는 대기로 남는다.

**실수했으면** — 전송 전이면 [주문서·전송]의 "최근 만든 묶음"에서 `되돌리기` 한 번에 취소되고 재고가 돌아옵니다. 전송 뒤에는 이카운트에서 전표를 먼저 지우고 여기서 `취소`.

**주문 변환을 꼭 해야 하나?** — 아니요. 자동 변환이 켜져 있으면 시스템이 매시간 알아서 만듭니다. 주문 변환 화면은 **시스템이 못 정한 것을 마무리하는 곳**이자, 만들기 전에 눈으로 한 번 더 보고 싶을 때 쓰는 도구입니다.

## 운영자용 — 이 흐름이 안전한 이유

| 단계 | 무엇이 일어나나 | 되돌릴 수 있나 |
|---|---|---|
| ① 수집 | 샵링커 주문이 하루 5번 원장(`core.orders`)에 쌓임. 같은 주문은 덮어씀 | 해당 없음 (읽기만) |
| ② 주문서 만들기 | 주문 1건 = 전표 1장(`ec.order_queue`). **재고가 이 시점에 빠짐.** 상태 "전송 대기" | **예** — 반대 방향 입고를 한 줄 더 쌓아 되돌림. 이력이 남음 |
| ③ 전송 | 이카운트 `SaveSaleOrder` 호출. 성공 → "전송 완료"+전표번호, 실패 → "전송 실패"(재시도 가능) | **아니요** — 이카운트에서 전표 삭제 후 여기서 개별 취소 |

**자동 변환의 규칙** (매시 35분)
- 최근 7일 샵링커 주문 중 아직 주문서가 아닌 것
- 모든 줄의 품목 후보가 **정확히 1개**
- 거래처코드 있음, 재고 충분
- → 만들어서 "전송 대기"에 둠. 전송은 하지 않음(사람이 누름)
- 나머지는 건드리지 않고 [주문 변환]에 남김. 만든 묶음은 `AUTO-`로 시작, 되돌리기 가능

**현재 비율** (최근 7일 634건 기준) — 자동 428건(68%) / 확인 필요 128건 / 코드 없음 78건. 담당자가 "기억"을 켜며 처리할수록 자동 비율이 오릅니다.

**권한** — 주문서 등록(`order`)과 이카운트 전송(`send`)은 별도 권한. [옵션·권한]에서 사람별로 켜고 끕니다. 지금 전송 권한: 박은지·고창재·지용현.

**알림** — 자동 변환이 주문서를 만들면 `sl.auto_made`, 전송이 실패하면 `ecount.order_failed` 이벤트가 나갑니다. [알림 관리]에서 잔디 방을 연결하면 그 방으로 갑니다.

**아직 확인 안 된 것 하나** — 이카운트 판매주문 API는 실제로 쏴 본 적이 없습니다. 첫 전송은 1건으로 하고 이카운트 화면(특히 영업담당 칸)을 확인하세요.

## 개발자용 — 어디에 무엇이 있나

**품목 매칭** `core.f_ec_cands(name, model, option)` → 후보 배열. 순위: ①상품명 전체=별칭 ②모델코드=별칭 ③모델코드=품목 ④상품명 안에 별칭 ⑤옵션 속 모델=별칭 ⑥옵션 속 모델=품목. ⑤⑥은 `opt:true`로 표시되며 **자동 적용하지 않음**(참고 후보). 첫 후보는 기존 `f_ec_code_of(name, model)`과 동일. 결과는 `ec.cand_cache`에 조합별 캐시(별칭·품목 변경 시 트리거로 비움).

**대기 목록** `core.f_sl_range(from, to, basis, q, channel, limit, include_done)` → 주문 단위로 묶음. 임시표 `_slp`를 남기며 `f_sl_auto`가 그걸 재사용. 공개 래퍼 `fn_sl_orders` / `fn_store_sl_orders(p_code, …)`.

**미리보기·생성** `core.f_sl_preview(nos, wh, picks)` / `core.f_sl_to_order(nos, wh, by, allow_neg, picks)`. `picks = {"주문번호#줄번호": "품목코드"}`. 생성 시 `batch_id` 부여 → `fn_order_void_batch(batch_id)`로 묶음 되돌리기.

**전송** `core.f_order_send(ids, by)` — 건별 결과 `detail[]` 반환. 래퍼 `fn_order_send`(admin) / `fn_store_order_send(p_code, ids)`(perm `send`).

**자동 변환** `core.f_sl_auto(days)` — `app_setting['sl_auto']='on'`일 때만 동작. 로그 `core.sl_auto_log`. pg_cron `sl-auto` 매시 35분. 관리자 API `fn_sl_auto_set / fn_sl_auto_run / fn_sl_auto_status`.

**화면** 공용 마법사 `web/_wiz/wiz.js`·`wiz.css` (마커 `WIZ:*:BEGIN/END`로 `admin.html`·`store.html`에 인라인). `wizMount(host, cfg)` — cfg로 rpc·함수명·권한을 주입해 두 화면이 같은 코드를 씀. 전송 확인창은 `ecSend({count, ids, run, onDone})`. 진행 상태는 `localStorage`(`dc_wiz`, `dc_wiz_store`)에 저장 → "이어서 하기".

**재고 되돌림 원칙** — 삭제하지 않는다. `inv.movement`에 `kind='in', ref_type='order_void'` 한 줄을 더 쌓는다. 누가 언제 무엇을 되돌렸는지 남는다.
